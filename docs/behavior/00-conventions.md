# Поведенческие конвенции

**Версия:** 2.0  
**Статус:** рабочий стандарт для всех `docs/behavior/*`

---

## 1. Зачем

Каждый модуль описывается так, чтобы разработчик **не додумывал** поведение. Если сценария нет в behavior-доке — его нет в продукте (или это явный gap → завести issue).

---

## 2. Формат сценария

Каждый сценарий:

```
### ID · Название
- Актёр: роль
- Предусловия: …
- Триггер: …
- Шаги: 1…n (UI + система)
- Результат: …
- Ошибки / отказы: …
- Аудит: что пишем в log
- Связи: какие сущности/модули затрагиваются
```

ID: `TT-CREATE-01`, `CASH-CLOSE-03`, `PAY-CALC-02` …

---

## 3. Роли (кратко)

| Код | Кто |
|---|---|
| `owner` | Владелец тенанта/сети |
| `admin` | Админ филиала |
| `master` | Мастер |
| `accountant` | Бухгалтер (касса/ЗП, без журнала — настраиваемо) |
| `client` | Клиент (онлайн) |
| `super` | Platform super-admin |

Матрица «действие × роль» — в каждом behavior-файле секция **Permissions**.  
Если право не указано — **запрещено**.

---

## 4. Общие правила данных

1. Все сущности scoped: `tenant_id` (+ `branch_id` где применимо).  
2. Время: UI в TZ филиала, storage UTC + `branch_tz` snapshot на appointment.  
3. Сетка журнала: шаг **5 минут** (snap); отображение меток — 15/30 по настройке.  
4. Деньги: integer **копейки** (minor units), валюта филиала (default RUB).  
5. Мягкое удаление где есть история (клиент, запись): `deleted_at` / статус `cancelled`, не hard-delete без права `owner`.  
6. Optimistic UI допустим только с явным rollback и toast ошибки.

## 5. Статусы записи (глобальная машина)

```
scheduled ──► confirmed ──► arrived ──► in_progress ──► completed
    │             │            │             │
    └─────────────┴────────────┴─────────────┴──► cancelled
                                      │
                                      └──► no_show
```

| Статус | Смысл |
|---|---|
| `scheduled` | Создана админом/онлайн, без доп. подтверждения |
| `confirmed` | Подтверждена (клиент/админ/авто) |
| `arrived` | Клиент в салоне |
| `in_progress` | Идёт услуга |
| `completed` | Услуга закончена (оплата может быть отдельно) |
| `cancelled` | Отменена (кто/почему в meta) |
| `no_show` | Не пришёл |

Переходы — только из белого списка в `01-timetable.md`.  
Оплата **не** является статусом записи; платёж — отдельная сущность.

## 6. Паттерны UI-поведения

| Паттерн | Правило |
|---|---|
| Destructive | Confirm modal: что удалится + необратимость |
| Drag | Ghost + snap preview + invalid = красный outline + snap-back |
| Save drawer | **Явная кнопка «Сохранить»** для записи (не автосейв критичных полей). Черновик локальный до Save |
| Toast | Успех 2с; ошибка — до dismiss + текст причины |
| Conflict | Hard-block (нельзя сохранить) vs Soft-warn (можно с confirm) — указано в сценарии |
| Offline | P1: нет офлайн-режима; при потере сети — баннер, блокировка Save |

## 7. Ошибки (коды для API/UI)

| Code | Когда |
|---|---|
| `FORBIDDEN` | Нет роли |
| `VALIDATION` | Поля |
| `CONFLICT_SLOT` | Пересечение слотов |
| `SHIFT_REQUIRED` | Нужна открытая смена |
| `SHIFT_CLOSED` | Смена закрыта, операция запрещена |
| `NOT_FOUND` | Сущность |
| `STALE` | Версия/etag устарела (кто-то изменил параллельно) |

UI всегда показывает human message на RU.

---

## 8. Аудит (минимум)

Пишем: actor_id, tenant_id, branch_id, entity, entity_id, action, before/after (diff), ip/ua (P2), timestamp.

Обязательный аудит: создание/отмена записи, drag-перенос, оплаты, закрытие смены, утверждение ЗП, смена прав.
