# Поведение: касса, оплаты, смены

**ID prefix:** `CASH-` / `PAY-` / `SHIFT-`  
**Фазы:** базовая оплата P1; смены P2; СБП/фискализация P3–P4  
**Связи:** appointment, client balance, loyalty, payroll, inventory

---

## 1. Сущности

### Payment
| Поле | Описание |
|---|---|
| id, tenant_id, branch_id | |
| appointment_id \| null | null = произвольный приход/расход |
| client_id \| null | |
| shift_id \| null | обязателен если policy `require_open_shift` |
| direction | `in` \| `out` |
| status | `pending` \| `posted` \| `refunded` \| `void` |
| lines[] | {type: service\|product\|tip\|debt\|loyalty, ref_id, title, amount_minor} |
| tenders[] | {method: cash\|card\|sbp\|transfer\|bonus\|certificate, amount_minor} |
| total_minor | sum(lines) |
| created_by, posted_at, version | |

**Инвариант:** `sum(tenders) == total_minor` для posted (исключение: сдача cash — tender cash = total, change_minor отдельно).

### CashShift
| Поле | Описание |
|---|---|
| id, tenant_id, branch_id | |
| opened_by, opened_at | |
| opening_cash_minor | факт наличных в ящике на старте |
| status | `open` \| `closing` \| `closed` |
| closed_by, closed_at | |
| declared_* | заявленные суммы при закрытии по методам |
| counted_cash_minor | пересчёт налички |
| variance_minor | counted − expected |
| variance_reason | обяз. если \|variance\| > threshold |
| note | |

**Инвариант:** в филиале **не более одной** `open` смены (P1). P4: несколько касс/устройств.

## 2. Permissions

| Действие | owner | admin | master | accountant |
|---|---|---|---|---|
| Открыть смену | ✓ | ✓ | ✗* | ✓ |
| Принять оплату | ✓ | ✓ | свои записи* | ✓ |
| Возврат | ✓ | ✓ | ✗ | ✓ |
| Закрыть смену | ✓ | ✓ | ✗ | ✓ |
| Править закрытую | ✓ | ✗ | ✗ | ✓ с audit |
| Просмотр Z-отчёта | ✓ | ✓ | ✗ | ✓ |

\* флаги филиала.

### Policy `require_open_shift`
- Default **true** для admin payments.  
- Если нет open shift → `SHIFT_REQUIRED`, CTA «Открыть смену».  
- Owner может override (флаг).

## 3. Открытие смены

### SHIFT-OPEN-01
- **Предусловия:** нет open смены на branch.  
- **Триггер:** Касса → «Открыть смену» / блокирующая модалка при первой оплате.  
- **Шаги:**  
  1. Ввод `opening_cash_minor` (обязателен, ≥0).  
  2. Optional note.  
  3. Confirm → status=`open`.  
- **Результат:** все последующие payments линкуются к shift_id.  
- **Аудит:** `shift.opened`.  
- **Ошибка:** уже open → показать текущую смену.

### SHIFT-OPEN-02 · Попытка второй смены
- Hard-block. Предложить закрыть текущую.

---

## 4. Оплата записи

### PAY-CREATE-01 · Полная оплата из drawer записи
- **Предусловия:** appointment существует; не cancelled; shift open если policy.  
- **Триггер:** «Принять оплату».  
- **Шаги:**  
  1. Собрать lines из услуг (+ товары P3) по snapshot цене.  
  2. Применить скидку / сертификат / бонусы (loyalty) → пересчёт.  
  3. Выбрать tenders (можно несколько: cash+card).  
  4. Если sum(tenders) < total → residual как долг клиента **или** hard «не хватает» — **default: разрешить частичную оплату**, долг на client.balance.  
  5. Если cash tender > остаток → change_minor.  
  6. Post → payment.status=`posted`; appointment.paid_total обновлён.  
- **UI:** сумма крупно, tenders список, кнопка «Провести».  
- **Аудит:** `payment.posted`.  
- **Связи:** loyalty burn/earn; payroll видит paid services.

### PAY-CREATE-02 · Частичная оплата
- Несколько payments на один appointment.  
- Badge: «Частично X / Y».  
- Нельзя превысить остаток (hard).

### PAY-CREATE-03 · Предоплата до визита
- Payment на appointment в статусе scheduled/confirmed.  
- Line type `deposit`.  
- При финальной оплате deposit учитывается.

### PAY-CREATE-04 · Оплата без записи (товар / прочий приход)
- appointment_id null; client optional.  
- Только admin+.

### PAY-CREATE-05 · Чаевые
- Line `tip` + tender; не входит в выручку услуг для % ЗП (настройка: tip_to_master true/false).

## 5. Возвраты и отмены оплаты

### PAY-REFUND-01 · Полный возврат
- **Предусловия:** payment posted; shift open (или отдельный expense в новой смене — **P1: только open shift**).  
- Создаёт payment direction=`out` linked `refund_of_id`.  
- Original → status=`refunded`.  
- Пересчёт appointment.paid_total.  
- Loyalty: reverse earn/burn.  
- Payroll: пересчёт периода если уже считали (см. PAYROLL-RECALC).

### PAY-REFUND-02 · Частичный возврат
- Сумма ≤ remaining refundable.  
- Указать lines.

### PAY-VOID-01 · Void ошибочного (день в день)
- До закрытия смены: void без движения денег наружу если tender ещё не «ушёл» — иначе refund.  
- **Правило P1:** void только cash same-shift; card → refund flow.

---

## 6. Долг клиента

### PAY-DEBT-01
- При частичной оплате `client.balance_minor` += недоплата (positive = клиент должен салону).  
- Погашение долга: отдельный payment lines type `debt`.  
- В карточке клиента — баланс и CTA «Погасить».

---

## 7. Закрытие смены

### SHIFT-CLOSE-01 · Старт закрытия
- **Триггер:** «Закрыть смену».  
- **Шаги:**  
  1. status → `closing` (блокирует новые payments; in-flight Save — дождаться или reject).  
  2. Система считает **expected** по методам из posted payments смены:  
     - expected_cash = opening_cash + cash_in − cash_out − change уже учтённая  
     - expected_card = sum(card)  
     - expected_sbp = …  
  3. UI показывает expected; админ вводит `counted_cash_minor` и confirms по безналу (или auto-accept card).  
  4. variance = counted_cash − expected_cash.  
  5. Если \|variance\| > threshold (default 0) → **обязателен** variance_reason.  
  6. Confirm → status=`closed`, snapshot totals immutable.  
- **Результат:** Z-отчёт смены (просмотр/печать P2).  
- **Аудит:** `shift.closed` + variance.

### SHIFT-CLOSE-02 · Отмена закрытия (во время closing)
- Если ещё не closed → вернуть `open` (только тот же user или owner).

### SHIFT-CLOSE-03 · Попытка оплаты в closing/closed
- `SHIFT_CLOSED` / block.

### SHIFT-CLOSE-04 · Повторное открытие после close
- Не reopen той же; только новая смена.  
- Корректировки закрытой — отдельный `adjustment` payment в новой смене + link (owner/accountant).

## 8. Отчёт смены (содержимое)

Обязательные блоки:
1. Время open–close, кто  
2. Opening cash  
3. Приходы по методам  
4. Расходы / возвраты  
5. Expected vs counted cash  
6. Variance + reason  
7. Список payments (expand)  
8. Выручка услуг vs товаров vs tips

## 9. Связь с журналом

| Событие журнала | Касса |
|---|---|
| Отмена с предоплатой | предложить PAY-REFUND |
| Complete без оплаты | badge, не блок статуса |
| Payment posted | блок записи: «Оплачено» |

Policy: можно ли менять услуги после оплаты?  
**Да, admin+**, с пересчётом: если новая сумма > paid → долг; если < → предложить refund разницы.

## 10. Edge cases

1. Два админа постят оплату одной записи одновременно → unique constraint на «полное покрытие» / version appointment.  
2. Отрицательный opening cash — запрет.  
3. Смена открыта 36+ часов — warning «забыли закрыть», не hard.  
4. Удаление пользователя, открывшего смену — смена остаётся, display «бывший сотрудник».  
5. Чаевые только картой — отдельный tender.  
6. Certificate tender > total — запрет / сдача на баланс сертификата (настройка; default запрет сдачи).

## 9. Фискализация 54-ФЗ и онлайн-оплата (этап 2 плана улучшений)

Провайдер подключается адаптером в коде (`registerFiscalProvider`, `registerAcquiringProvider`). Пока договоров нет, работает провайдер `test`: чеки получают выдуманные ФН/ФД/ФП, оплата проходит в песочнице на нашей странице.

### FISC-SELL-01 · Чек на каждую оплату
- Если в филиале включены чеки, каждый проведённый платёж в той же транзакции превращается в документ чека (`fiscal_receipts`, статус `pending`).
- Сразу после ответа API чек отправляется провайдеру. Всё, что не ушло, cron досылает раз в 5 минут (`POST /api/jobs/fiscal`).
- Состав чека:
  - услуга идёт как `service` / полный расчёт;
  - товар как `commodity`;
  - предоплата, сертификат и абонемент как аванс (`advance`, предмет «платёж»);
  - погашение долга как `credit_payment`.
- Чаевые в чек не входят: это не выручка салона. Их сумма снимается сначала с наличных, потом с безнала.
- Бонусы уменьшают цену позиций пропорционально (скидка). Сертификат и абонемент идут в чеке как «зачёт предоплаты».
- Покупатель в чеке: телефон и почта клиента, если они известны.

### FISC-ADVANCE-01 · Зачёт аванса
- Первая оплата визита с услугами закрывает все ещё не зачтённые предоплаты по этой записи.
- В таком чеке услуги идут по полной цене, а сумма предоплат стоит в чеке как «зачёт предоплаты».

### FISC-REFUND-01 · Возврат
- Возврат (`direction = out`) даёт чек «возврат прихода» по строкам возврата.

### FISC-VOID-01 · Аннулирование
- Если чек ещё не ушёл, он отменяется (`canceled`).
- Если чек уже пробит, создаётся чек «возврат прихода» на ту же сумму.

### FISC-RETRY-01 · Ошибки
- Временная ошибка: повтор через 1, 2, 4… минут, но не реже раза в 60 минут, всего до 10 попыток.
- Ошибка без повтора, или попытки кончились: статус `failed`.
- В кассе появляется плашка и вкладка «Чеки» с кнопкой «Повторить». Повтор подставляет актуальные ИНН, адрес и систему налогообложения из настроек.

### Настройки
- Включает и меняет только владелец.
- Поля: ИНН (10 или 12 цифр), адрес расчётов, система налогообложения, НДС, провайдер кассы, провайдер оплаты и срок жизни ссылки.
- Чеки нельзя включить без ИНН и адреса.

### ACQ-LINK-01 · Ссылка на оплату (карта, СБП)
- Создаётся в записи, вкладка «Оплата», на сумму не больше остатка.
- Если запись ещё не началась и сумма меньше остатка, это предоплата. Иначе это оплата визита.
- Новая ссылка отменяет прежнюю неоплаченную.
- Ссылка живёт `acquiring_link_hours`, затем истекает.
- Страница клиента `/pay/{token}`: сумма, визит, кнопка оплаты. В тестовом режиме три кнопки: карта, СБП, отказ.
- Успешная оплата проводит обычный платёж:
  - способ `card` или `sbp`;
  - без смены, потому что деньги у банка, а не в ящике;
  - автор «Онлайн-оплата».
- По этому платежу пробивается чек.
- Повторное уведомление провайдера ничего не меняет.

### ACQ-LINK-02 · Оплата без остатка
- Если клиент оплатил ссылку, когда визит уже оплачен на кассе или отменён, деньги всё равно учитываются как прочий приход.
- Ссылка помечается: «Оформите возврат клиенту».

### Не сделано
- Боевые адаптеры (АТОЛ Онлайн, ЮKassa и т.п.) и проверка подписи вебхука: ждут выбора провайдера и ключей.
- Предоплата при онлайн-записи (OB-PAY-01).
- Отправка ссылки клиенту сообщением: будет на этапе 3 плана, «Сообщения».
- Чек коррекции и Z-отчёт ККТ.

## 10. Своя касса и терминал, допродажи

### PAY-EXT-01 · Оплата на своём терминале
- В настройках есть режим «Чеки: на своей кассе и терминале». Он исключает онлайн-кассу через CRM, переключает владелец.
- При оплате администратор вносит сумму и способ вручную. Можно указать номер чека с кассы и код операции терминала (RRN или код авторизации, до 40 символов, необязательно).
- Для карты и СБП кнопка называется «Оплачено на терминале».
- CRM в этом режиме собственных чеков не отправляет.
- То же доступно в «+ Приход» и при возврате (`receiptNo`).

### PAY-EXT-02 · Номер чека позже
- В деталях платежа «Указать / Изменить» сохраняет номер чека и код терминала (`PATCH /payments/:id/refs`).
- Изменение пишется в аудит.
- Права: owner, admin, accountant.

### PAY-UPSELL-01 · Допродажа в оплате визита
- Во вкладке «Оплата» записи можно добавить товары из склада.
- Услуги, товары и чаевые проходят одним платежом и одним чеком, остаток на складе списывается.
- Если денег меньше суммы, сначала покрываются товары и чаевые, остаток идёт в счёт услуг, недостача по услугам становится долгом.
- Товары можно продать и к уже оплаченной записи.
- Оплата товаров бонусами, сертификатом или абонементом пока не поддерживается.
