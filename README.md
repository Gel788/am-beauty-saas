# Am Beauty

Мультитенантная CRM салона красоты: журнал записей, клиенты, услуги, мастера и их график, онлайн-запись, касса со сменами, отчёт дня, напоминания, зарплаты, склад и лояльность. Интерфейс на русском. Сделаны фазы 1–3 по `docs/TZ.md`. Как развернуть на сервере, описано в `docs/DEPLOY.md`.

Поведение продукта описано в `docs/behavior`. Если сценария там нет, его нет и в продукте.

## Запуск

Нужны Node.js 22 и Postgres 16.

```bash
docker compose up -d
cp .env.example .env
npm install
npm run db:migrate
npm run db:seed
npm run dev
```

Приложение: http://127.0.0.1:43123

Миграции идут от суперпользователя (`MIGRATE_URL`), приложение подключается как `app_user` и подчиняется RLS. `npm run db:migrate` применяет файлы из `db/migrations` по порядку и помнит их в `schema_migrations`; база, созданная до появления раннера, подхватывается автоматически (001 помечается применённой, дальше идут новые). В Docker это `postgres` / `postgres` и база `ambeauty` на порту 5432.

## Онлайн-запись

Страница для клиентов: `/b/{салон}/{филиал}`, у демо-салона это http://127.0.0.1:43123/b/am-beauty/sadovaya. Её можно встроить на сайт через iframe; ссылку, код вставки и правила (шаг слотов, запись не раньше чем через N минут, горизонт, время брони, окно отмены, лимит записей на телефон) владелец настраивает в «Настройках».

Клиент проходит три шага: услуга, мастер и время, контакты. Выбранное время держится за ним 5–10 минут (`slot_holds`), подтверждение создаёт запись с `source = online`, а клиента находит по телефону или создаёт. После записи клиент получает ссылку `/booking/{token}`: до окна отмены запись отменяется сама, позже уходит просьбой администратору (видна в истории записи).

Публичные запросы идут без сессии. Салон находят функции `public_branch_lookup` и `public_booking_lookup` (SECURITY DEFINER, возвращают только id), дальше всё работает под RLS этого салона.

## Отчёт дня

Раздел «Отчёт дня» (`/reports`, владелец, администратор, бухгалтер) показывает за выбранный день выручку по проведённым оплатам за вычетом возвратов с разбивкой на услуги, товары и чаевые и по способам оплаты, записи по итогам (завершено, отменено, неявки, онлайн), загрузку мастеров (занятое время к рабочему по графику) и списки платежей и записей дня.

## Напоминания

За `reminder_hours` часов до визита (по умолчанию 24) клиент получает напоминание, один раз на запись. С 22:00 до 09:00 по времени филиала сообщения не уходят и ждут утра. Канал отправки пока не подключён: канал `log` записывает текст в журнал (`outbound_messages`, «Настройки» → «Журнал сообщений»). Реальный канал (Telegram, SMS) добавляется через `registerChannel` в `src/server/reminders.ts` и список `tenants.message_channels`; каналы перебираются по порядку, пока один не доставит.

Задачу запускает cron, например каждые 10 минут:

```bash
curl -fsS -X POST -H "x-jobs-token: $JOBS_TOKEN" http://127.0.0.1:43123/api/jobs/reminders
```

Без `JOBS_TOKEN` в окружении эндпоинт закрыт.

## Зарплаты мастеров

Раздел «Зарплаты» (`/payroll`). Правила оплаты: процент с услуги (от цены или от оплаченного), фикс за услугу, оклад (в месяц, за 2 недели, в неделю) и оклад + процент; чаевые мастеру можно выключить. Порядок поиска правила: мастер + услуга → мастер → правило для всех. Два правила одного уровня на одну дату не сохраняются; ставку меняют датой окончания старого правила и новым правилом. Правило, уже попавшее в утверждённый расчёт, при удалении закрывается датой, а не удаляется.

Период: черновик → рассчитан → утверждён → выплачен → закрыт. Расчёт берёт завершённые визиты по дате завершения (`completed_at`), пропускает визиты, исключённые из зарплаты (`POST /api/appointments/:id/payroll-exclusion`, причина обязательна), и предупреждает о визитах без оплаты (их можно начислять, включив `accrue_on_complete_unpaid` у филиала), о визитах без правила и о записях поверх другой. Оклад делится пропорционально длине периода. Возврат по услуге, уже вошедшей в утверждённый период, даёт строку «Сторно» в периоде, где проведён возврат. Если итог мастера отрицательный, к выплате 0, а долг виден в ведомости. Премии, штрафы и корректировки (бухгалтер или владелец, с причиной) переживают пересчёт. Утверждает и выплачивает бухгалтер или владелец, по одному мастеру или всем; снять утверждение нельзя после первой выплаты; закрывает период владелец. Мастер видит только свою ведомость и только после утверждения. Периоды одного филиала не пересекаются.

API: `GET|POST /api/payroll/rules`, `PATCH|DELETE /api/payroll/rules/:id`, `GET|POST /api/payroll/periods`, `GET /api/payroll/periods/:id`, `POST /api/payroll/periods/:id/{calculate,approve,unapprove,pay,lock,lines}`, `DELETE /api/payroll/periods/:id/lines/:lineId`.

Пока нет: доля ассистента (нет поля ассистента в записи), «цена после скидки» считается как цена услуги, выгрузка ведомости в PDF.

## Склад

Раздел «Склад» (`/inventory`). Номенклатура с уникальным артикулом, единицей (шт, мл, г, уп), себестоимостью за единицу и ценой продажи; позицию с движениями нельзя удалить, она уходит в архив. Остатки ведутся по филиалам с точностью до тысячных. Каждое изменение остатка — движение в журнале: приход (поставщик, номер документа, цена закупки становится себестоимостью), списание с причиной, перемещение между филиалами (две связанные строки в одной транзакции), продажа, расход на услугу, инвентаризация. По умолчанию остаток не уходит в минус; разрешить это можно в настройках филиала.

Расход на услуги: на услугу задаются материалы и количество. Когда визит завершают, материалы списываются со склада филиала. Если остатка не хватает, по умолчанию визит завершается, движение помечается «в минус» и администратор видит предупреждение; политика `block` не даёт завершить визит. Полный возврат денег за услугу возвращает её материалы на склад (один раз).

Продажа: в кассе «+ Приход» → «Товар со склада» проводит чек с товаром и списывает его; возврат товара по чеку и аннулирование возвращают остаток. Инвентаризация фиксирует ожидаемые остатки, принимает факт и проводит разницу (факт − ожидание), поэтому продажи во время пересчёта не теряются; отчёт показывает недостачу и излишек по себестоимости.

В зарплате правило с флагом «минус материалы» считает процент от цены за вычетом себестоимости израсходованных материалов (не ниже нуля).

API: `GET|POST /api/inventory/items`, `PATCH|DELETE /api/inventory/items/:id`, `GET /api/inventory/movements`, `POST /api/inventory/{receipt,write-off,transfer}`, `GET|PUT /api/inventory/consumables/:serviceId`, `GET|POST /api/inventory/counts`, `GET /api/inventory/counts/:id`, `PUT /api/inventory/counts/:id/lines`, `POST /api/inventory/counts/:id/{apply,cancel}`. Продажа — `POST /api/payments` с `kind: "misc"` и `items: [{ itemId, qty }]`.

## Мастера и график

Экран «Мастера» (`/staff`) по `docs/behavior/03-services-staff.md` §2–4:

- Профиль мастера: имя, специализация, цвет, онлайн-запись, филиалы. Деактивация спрашивает, что сделать с будущими записями: перенести к другому мастеру или отменить. История остаётся.
- Неделя по филиалу: несколько рабочих интервалов и перерывы в день, кнопка «на будни» копирует день на пн–пт. Пересечения и перерыв вне рабочих часов не сохраняются (SCH-CONFLICT-01).
- Исключения: выходной, отпуск (диапазон), особые часы на день. Если на эти дни уже есть записи, система предупреждает и сохраняет только после подтверждения. Записи не трогаются. «Повторить эту неделю на следующей» копирует исключения недели.
- Журнал заштриховывает время вне рабочих часов и перерывы, но клик там по-прежнему создаёт запись (SCH-VIEW-01).
- Мастер видит только свой график («Мой график») и не меняет его сам: он предлагает новую неделю или просит выходной, администратор согласует или отказывает с комментарием во вкладке «Запросы мастеров». Мастер может отозвать свой запрос.
- Меню зависит от роли: мастер видит календарь, клиентов, свой график и свою зарплату; бухгалтер — финансы, склад, отчёт дня и зарплаты и после входа попадает в кассу.

## Лояльность

Экран «Лояльность» (`/loyalty`) по `docs/behavior/07-loyalty.md`:

- **Бонусы.** Программа включается в настройках, по умолчанию выключена. Начисление — процент от оплаты деньгами (5%), на чаевые, долги и часть чека, оплаченную бонусами, сертификатом или абонементом, баллы не начисляются. Списание — не больше заданной доли визита (30%), в том числе когда визит оплачивают в несколько платежей. Возврат возвращает потраченные баллы и списывает начисленные пропорционально, баланс не уходит в минус. Ручная корректировка — администратор, с причиной.
- **Сертификаты.** Продаются в кассе («+ Приход» → «Сертификат»), код вида `XXXX-XXXX`. Оплачивают визит или товар частями, сдачи с сертификата нет, возврат возвращает сумму на сертификат. Истёкший не принимается. Аннулирует только владелец.
- **Абонементы.** Владелец или администратор заводит виды (визиты, срок, услуги), администратор продаёт их клиенту в кассе. Один визит абонемента закрывает одну подходящую услугу записи. Заморозка один раз, до 90 дней, сдвигает срок; продление с причиной.
- **Промокоды.** Процент или сумма, даты, минимальный чек, услуги, общий лимит и лимит на телефон, «только онлайн». Применяется в онлайн-записи или в карточке визита до оплаты. Цены услуг пересчитываются, исходные сохраняются; смена услуг или отмена записи снимает промокод. Зарплата по правилу «база» считается от цены до скидки.
- Бонусы, сертификаты и абонементы — способы оплаты, а не деньги: в смене они не ждут денег в ящике, а отчёт дня показывает, сколько выручки пришло деньгами.

## Чеки и онлайн-оплата

В настройках филиала владелец включает чеки по 54-ФЗ и оплату по ссылке (карта, СБП). Пока провайдер не выбран, работает тестовый режим: чеки получают выдуманные фискальные признаки, оплата проходит на странице `/pay/...` кнопкой. Каждая оплата, возврат и аннулирование дают чек. Статус видно в платеже, а все чеки собраны на вкладке «Чеки» в кассе. Ссылку на оплату создают в записи, на вкладке «Оплата». Правила описаны в `docs/behavior/04-cash-shifts.md` §9. В демо-данных всё это включено для филиала Садовая.

## Что входит в эту фазу

**Фаза 1.** Авторизация, тенант и филиал, роли, услуги, мастера и недельный график, клиенты, журнал (создание, правка, отмена, статусы, конфликты, перенос и изменение длительности), открытие смены и проведение оплаты.

**Фаза 1b — касса** (`docs/behavior/04-cash-shifts.md`):

- Закрытие смены в два шага: «Закрыть смену» переводит её в `closing` и блокирует новые оплаты, возвраты и аннулирования; затем пересчёт наличных, сверка безнала и Z-отчёт (SHIFT-CLOSE-01). Пока смена закрывается, её можно вернуть в работу — тому, кто начал, или владельцу (SHIFT-CLOSE-02). Закрытая смена не переоткрывается, её итоги заморожены снимком (SHIFT-CLOSE-03/04).
- Ожидаемые суммы по способам: наличные = старт + приход − возвраты (сдача уже вычтена), безнал принимается по ожидаемому, если кассир не ввёл другое. Расхождение больше порога филиала (`shift_variance_threshold_minor`, по умолчанию 0) или несовпадение безнала требует причину.
- Возвраты полные и частичные (PAY-REFUND-01/02): по сумме или по строкам, не больше остатка, деньги уходят тем же способом, что пришли (безнал первым). Возврат проводится в текущей открытой смене. Полностью возвращённый платёж получает статус `refunded`; возврат погашения долга возвращает долг клиенту.
- Аннулирование (PAY-VOID-01): только наличные, только в той же ещё открытой смене и без возвратов; причина обязательна. Остальное — через возврат.
- Оплаченная сумма записи, долг и выручка дашборда считаются нетто: приход минус возвраты, аннулированные не учитываются.
- В филиале не больше одной активной (`open` или `closing`) смены. Предупреждение, если смена открыта 36+ часов.
- Экран «Касса»: текущая смена, ожидаемое по способам, разбивка выручки, платежи с возвратом и аннулированием, приход без записи, история смен, Z-отчёт с печатью. В карточке записи — список платежей и возврат; при отмене предоплаченной записи карточка сама предлагает возврат.
- Аудит: `shift.opened`, `shift.closing_started`, `shift.closing_cancelled`, `shift.closed` (с расхождением), `payment.posted`, `payment.refunded`, `payment.voided`.

API кассы: `GET /api/shifts`, `GET /api/shifts/current`, `POST /api/shifts/open`, `POST /api/shifts/:id/start-closing`, `POST /api/shifts/:id/cancel-closing`, `POST /api/shifts/:id/close`, `GET /api/shifts/:id/report`, `GET /api/payments?shiftId=|date=`, `POST /api/payments/:id/refund`, `POST /api/payments/:id/void`, `GET /api/appointments/:id/payments`.

Не сделано: неделя/месяц в журнале, онлайн-запись и модули фаз 2–4, корректировки закрытой смены отдельным `adjustment`-платежом (SHIFT-CLOSE-04, вторая часть). Не было файлов `design-direction.md` и `yclients-parity-matrix.md` — экран кассы собран в стиле утверждённых макетов журнала и дашборда.
